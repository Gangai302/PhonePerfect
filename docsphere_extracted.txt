P25 [Heading 1] (align=CENTER (1)): ABSTRACT
P26 [Normal] (align=None): Modern mobile users handle an extensive collection of sensitive documents—such as identity cards, medical records, tax forms, receipts, and invoices—on their smartphones. Existing document management applications and virtual assistants rely predominantly on remote cloud computing services, exposing personally identifiable information (PII) to potential network interception, data breaches, and recurring cloud subscription costs. Furthermore, mobile search capabilities typically fail on unstructured scans and photos due to the absence of local optical character recognition and semantic understanding. This report presents DocSphere AI, a completely secure, privacy-preserving, on-device document intelligence and multimodal retrieval-augmented generation (RAG) system built natively for Android.
P27 [Normal] (align=None): The system is developed in modern Kotlin with Jetpack Compose and Material 3, incorporating Google MediaPipe GenAI for local Small Language Model (SLM) inference using Gemma 2B (INT4 quantized) and Google ML Kit on-device Text Recognition for optical character recognition. Scanned physical documents and images are downscaled through a multi-resolution pipeline to a maximum dimension of 2048 pixels to ensure high recognition accuracy while preventing out-of-memory exceptions. Text and structured fields (including Aadhaar, PAN, SSN, dates, invoice amounts, and contact details) are deterministically extracted and indexed within a local Room SQLite database augmented with Full-Text Search (FTS4) and BM25 relevance ranking. An adaptive Dual-Engine AI Routing architecture automatically determines whether a user query is fulfilled entirely on-device through Gemma 2B or routed to Google Gemini 1.5 Flash/Pro with client-side sensitive data scrubbing and explicit user consent.
P28 [Normal] (align=None): To ensure seamless execution on resource-constrained mobile hardware, DocSphere AI enforces an on-device prompt token budget of approximately 450 tokens (~1800 characters) with dynamic chunk truncation and executes all retrieval workflows on asynchronous background I/O coroutines, preventing UI thread blocking and SQLite lock contention. A concurrency coordinator with strict mutex locks serializes local model inferences to prevent device overheating and memory exhaustion. In addition, DocSphere provides optional encrypted cloud synchronization with Google Drive via OAuth 2.0 PKCE. Experimental evaluation demonstrates sub-second full-text retrieval, zero cloud data leakage for offline interactions, and reliable on-device inference within a 1.8 GB memory footprint, establishing a new paradigm for privacy-first mobile document intelligence.
P29 [Normal] (align=None): Keywords: On-device intelligence, small language models, Gemma 2B, retrieval-augmented generation, mobile document intelligence, optical character recognition, Room SQLite FTS4, privacy-preserving AI, Android, Kotlin.

P108 [Heading 2] (align=None): 1.1 DESCRIPTION
P109 [Normal] (align=None): In the modern digital era, individuals and professionals store an ever-increasing volume of crucial personal, financial, academic, and legal documents directly on their mobile devices. These files include government identity cards, health insurance policies, medical prescriptions, tax assessments, bank statements, academic degrees, and utility invoices. When users need to locate a specific clause, retrieve an identity number, or extract an expenditure amount from an older document, they typically face significant obstacles. Standard mobile file managers only offer simple filename matching, failing completely when searching within unstructured document bodies or scanned photographic images.
P110 [Normal] (align=None): DocSphere AI is an intelligent, privacy-first mobile document management and cognitive retrieval subsystem developed natively for Android. The application autonomously scans the device storage, ingests documents in various formats (PDF, DOCX, TXT, PNG, JPEG), extracts text using on-device optical character recognition, performs deterministic field extraction, and indexes the contents into a high-performance local SQLite database with full-text search (FTS4). DocSphere AI integrates an on-device Small Language Model (Gemma 2B) powered by Google MediaPipe GenAI, enabling users to engage in natural language conversations with their document library completely offline, without transmitting sensitive personal records over the internet.
P111 [Normal] (align=None): The foundational principle of DocSphere AI is that personal privacy and data sovereignty must never be compromised for intelligence. By executing OCR, text chunking, BM25 keyword retrieval, and neural language reasoning directly on the smartphone's hardware (CPU, GPU, and NPU), the system guarantees zero data leakage for offline operations. For complex analytical queries where additional synthetic capability is desired, DocSphere provides a Dual-Engine AI Routing architecture that allows users to optionally leverage Google Gemini 1.5 Flash/Pro with client-side PII scrubbing and explicit consent. This design achieves an optimal balance between total privacy, instantaneous retrieval, and high-accuracy document intelligence.
P112 [Heading 2] (align=None): 1.2 DOMAIN SPECIFICATION
P113 [Normal] (align=None): The project operates at the confluence of three vital domains in computer science: mobile edge computing, on-device natural language processing with Small Language Models, and local information retrieval. A technical overview of each domain is presented below so that the subsequent architectural and engineering decisions can be thoroughly understood.
P114 [Heading 3] (align=None): 1.2.1 Mobile Edge Computing and On-Device Intelligence
P115 [Normal] (align=None): Mobile edge computing shifts intensive computational tasks—such as computer vision, machine learning inference, and database query indexing—away from centralized remote cloud servers directly to end-user handheld devices. With modern mobile system-on-chip (SoC) architectures integrating specialized Neural Processing Units (NPUs) and high-throughput mobile GPUs, smartphones possess sufficient parallel computing capability to execute complex machine learning models locally. Running intelligence workloads at the edge delivers three paramount advantages: complete user privacy with zero cloud data transmission, resilience against network outages and offline availability, and the complete elimination of expensive recurring cloud infrastructure costs.
P116 [Heading 3] (align=None): 1.2.2 Small Language Models (SLMs) and MediaPipe Inference
P117 [Normal] (align=None): Small Language Models (SLMs) represent compact neural architectures (typically ranging from 1 billion to 3 billion parameters) trained on high-quality synthetic and curated datasets. Unlike massive cloud-hosted Large Language Models (LLMs) that require multiple enterprise-grade GPUs, SLMs are optimized for resource-constrained edge execution through aggressive post-training quantization, such as 4-bit integer (INT4) weight representations. Google's Gemma 2B model, when paired with the MediaPipe GenAI runtime framework, enables real-time text comprehension, question answering, and contextual reasoning within an Android mobile application's memory envelope of approximately 1.5 to 2.0 gigabytes.
P118 [Normal] (align=None): While SLMs exhibit remarkable reasoning capabilities on mobile hardware, they operate under strict constraints compared to cloud models. Edge devices possess limited working RAM and strict thermal dissipation limits. Consequently, language generation on mobile must enforce disciplined prompt token budgets, strict context window management, and robust inference coordination to prevent system-wide out-of-memory (OOM) aborts and device overheating.
P119 [Heading 3] (align=None): 1.2.3 On-Device Retrieval-Augmented Generation and SQLite FTS
P120 [Normal] (align=None): Retrieval-Augmented Generation (RAG) grounds the generation of a language model by retrieving relevant factual excerpts from an external knowledge repository and providing them as context within the prompt. In mobile environments where loading large neural embedding models and vector similarity indexers can exhaust volatile memory, hybrid lexical retrieval systems offer superior efficiency. SQLite with the Full-Text Search (FTS4) module and Okapi BM25 relevance ranking delivers lightning-fast, sub-millisecond keyword and token matching directly on the Android file system with virtually zero memory overhead. Coupling FTS4 chunk retrieval with deterministic regex entity extraction ensures that the Small Language Model receives precisely targeted factual context.
P121 [Heading 2] (align=None): 1.3 PROBLEM STATEMENT
P122 [Normal] (align=None): Mobile document storage is overwhelmingly unstructured, fragmented across various folders, and dominated by scanned images and PDF files whose contents are completely invisible to standard OS-level file search. Existing mobile productivity and document assistant solutions rely almost exclusively on uploading full document files to third-party cloud AI servers for OCR and language model inference. This architectural dependence creates severe security and privacy hazards: sensitive personal documents containing government identity numbers, financial records, medical histories, and confidential signatures are exposed to remote data interception, third-party storage logging, and unauthorized cloud mining.
P123 [Normal] (align=None): Furthermore, cloud-dependent assistants suffer from severe latency penalties, fail completely during travel or in environments with poor network connectivity, and incur prohibitive recurring API subscription costs. Conversely, attempting to run uncoordinated AI models locally on mobile devices frequently triggers fatal Out-Of-Memory (OOM) crashes, UI freezes, battery drain, and hallucination of critical identity values. Therefore, there is an urgent need for an autonomous, robust, and completely privacy-preserving on-device document intelligence system that combines multi-resolution vision OCR, deterministic entity extraction, local FTS4 retrieval, and strict prompt token budgeting to enable secure, offline, natural language document interaction on Android smartphones.

EXISTING SYSTEM
P162 [Normal] (align=None): Currently, users seeking to manage, search, and understand documents on mobile devices rely on three primary paradigms. Each approach exhibits significant architectural weaknesses when evaluated against privacy, latency, and resource constraints.
P163 [Heading 2] (align=None): 3.1 CLOUD-DEPENDENT DOCUMENT ASSISTANTS
P164 [Normal] (align=None): The predominant class of mobile document tools relies completely on cloud services (such as Google Drive Assistant, Adobe Acrobat AI, and Microsoft Copilot). When a user requests a summary or asks a question about a document, the mobile app uploads the entire PDF or image file to remote cloud servers. Cloud-hosted OCR engines extract text, large cloud vector databases generate embeddings, and massive LLMs (GPT-4 or Gemini Ultra) process the prompt. While this provides high linguistic fluency, it suffers from fatal drawbacks: users must surrender absolute confidentiality over private records, high latency degrades responsiveness, network disconnection causes total system failure, and expensive recurring subscription fees are imposed.
P165 [Heading 2] (align=None): 3.2 TRADITIONAL RULE-BASED AND KEYWORD FILE EXPLORERS
P166 [Normal] (align=None): The second conventional approach consists of standard mobile file managers (e.g., Samsung My Files, Files by Google). These applications index files purely based on filesystem metadata, such as file name, modification timestamp, file size, and extension. They perform no internal content inspection, optical character recognition, or semantic entity extraction. As a result, searching for a specific expense, policy number, or medical diagnostic term yields zero results if that keyword is not explicitly written in the filename. Furthermore, these applications lack all cognitive reasoning capability, unable to answer questions or synthesize information across multiple documents.
P167 [Heading 2] (align=None): 3.3 HEAVY UNOPTIMIZED ON-DEVICE REASONING ENGINES
P168 [Normal] (align=None): A recent emerging category comprises experimental mobile apps that attempt to load open-source language models directly on smartphones without coordination or system-level constraints. These applications typically attempt to load unquantized or poorly optimized models directly into volatile RAM, failing to manage concurrent background tasks or memory allocation. When users process complex documents or multi-page scans, these applications routinely trigger Android low-memory killer (LMK) events, causing abrupt app termination, severe thermal throttling, and battery depletion.
P169 [Heading 1] (align=CENTER (1)): CHAPTER 4
PROBLEMS IDENTIFIED
P170 [Normal] (align=None): A comprehensive investigation of existing systems and mobile operating constraints identified seven fundamental challenges that severely impair mobile document intelligence:
P171 [Heading 2] (align=None): 4.1 PRIVACY RISKS AND PII LEAKAGE IN CLOUD SYSTEMS
P172 [Normal] (align=None): Uploading personal documents to cloud servers creates grave security vulnerabilities. Identity proofs, bank statements, and medical reports contain Personally Identifiable Information (PII) protected by regulations like GDPR and HIPAA. Cloud transmission exposes data to man-in-the-middle network attacks, server-side data leaks, and commercial model training on private user records without explicit consent.
P173 [Heading 2] (align=None): 4.2 HIGH LATENCY AND COMPLETE OFFLINE UNAVAILABILITY
P174 [Normal] (align=None): Cloud-based document analysis introduces unavoidable network latency, frequently requiring 5 to 15 seconds per query depending on connection quality and file upload sizes. In remote environments, during transit, or during network disruptions, cloud assistants fail entirely, rendering users incapable of accessing crucial document information when it is most urgently needed.
P175 [Heading 2] (align=None): 4.3 MOBILE OUT-OF-MEMORY (OOM) AND SYSTEM FREEZES
P176 [Normal] (align=None): Android smartphones enforce strict per-process memory limits. Ingesting high-resolution camera scans (e.g., 4000x3000 pixels at 48MB uncompressed bitmap) directly into memory alongside a 1.5 GB Small Language Model and active database instances easily exceeds device heap thresholds, triggering catastrophic Out-Of-Memory exceptions and operating system crashes.
P177 [Heading 2] (align=None): 4.4 POOR RECOGNITION ACROSS SCANNED DOCUMENTS AND IMAGES
P178 [Normal] (align=None): Millions of real-world documents are captured as photographic scans or camera snapshots rather than clean digital PDFs. Standard file indexing ignores image content entirely. When OCR is applied naively without preprocessing, varying orientations, noise, and excessive image resolutions cause recognition failures or unhandled buffer allocations.
P179 [Heading 2] (align=None): 4.5 PROMPT TOKEN BUDGET OVERFLOW IN MOBILE SLMS
P180 [Normal] (align=None): Mobile Small Language Models like Gemma 2B INT4 possess constrained context windows (typically 2048 tokens) and degrade rapidly in generation speed as input length grows. Concatenating full multi-page document texts into the model prompt causes immediate prompt token budget overflow, producing incoherent responses, truncated outputs, or inference engine crashes.
P181 [Heading 2] (align=None): 4.6 CONCURRENCY CONFLICTS AND SQLITE LOCK CONTENTION
P182 [Normal] (align=None): Executing database queries, full-text FTS searches, and background OCR indexing concurrently on the main UI thread causes noticeable frame drops, application unresponsive (ANR) dialogs, and SQLite database lock contention errors (SQLiteException: database is locked) when background workers attempt simultaneous write transactions.
P183 [Heading 2] (align=None): 4.7 HALLUCINATION OF SENSITIVE STRUCTURED VALUES
P184 [Normal] (align=None): Neural language models are probabilistic text generators that cannot inherently guarantee numerical arithmetic or verbatim string precision. When asked for an exact 12-digit Aadhaar number, a 10-digit PAN, or a specific financial transaction total, generative models can subtly hallucinate incorrect digits, leading to dangerous errors in financial and legal contexts.

P249 [Heading 3] (align=None): 7.2.2 Multi-Resolution Vision OCR and Text Preprocessing Module
P250 [Normal] (align=None): Scanned receipts, photographed identity cards, and mobile camera captures do not contain extractable digital text streams. The Multi-Resolution Vision OCR and Text Preprocessing Module transforms unstructured visual content into structured digital text entirely on-device using Google ML Kit Text Recognition.
P251 [Normal] (align=None): When processing large camera images (often exceeding 12 megapixels), loading raw uncompressed bitmaps into memory can instantly trigger an Out-Of-Memory (OOM) crash. DocSphere AI implements a specialized multi-resolution preprocessor (MultiResolutionScaler) that inspects image dimensions using BitmapFactory.Options.inJustDecodeBounds. If the image's maximum dimension exceeds 2048 pixels, it is proportionally downscaled. Empirical validation proves that 2048px preserves full OCR text legibility down to 6pt font while reducing memory allocation from over 48 MB to less than 12 MB per image.
P252 [Normal] (align=None): Once downscaled, the bitmap is supplied to OcrIndexingWorker. The worker executes ML Kit's on-device neural recognizer, extracting hierarchical text elements: text blocks, lines, and recognized words along with coordinate bounding boxes. The extracted text is normalized, stripped of non-printable noise characters, and passed downstream for chunking and field parsing.

P254 [Heading 3] (align=None): 7.2.3 Deterministic Field Extraction and PII Sanitization Module
